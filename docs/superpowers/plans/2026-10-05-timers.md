# Timers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (chosen: native) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a parent start a timer for a kid that, after N minutes, locks the computer or closes games until lifted or midnight.

**Architecture:** A `Timer` in `protocol::rules` feeds a new `decide_with_timer`, which the server and the agent both use; the
timer travels in each `AccountSnapshot`. The server stores one timer per account and exposes start/cancel endpoints; the
dashboard adds timer controls to each kid's card. The agent's enforcement code is unchanged apart from passing the timer in.

**Tech Stack:** Rust 2024 (protocol, agent, server), axum, rusqlite, chrono, vanilla JS.

**Spec:** `docs/superpowers/specs/2026-10-05-timers-design.md`

## Global Constraints

- `cargo add` for dependencies; `cargo +nightly fmt`; gate: fmt --check, clippy `-D warnings`, `test --locked`.
- Timer minutes 1..=240; modes `lock` (default) and `games`.
- A timer only ends things sooner. Precedence for `computer`: blackout, then timer ended, then outside schedule.
- The stop lasts until "Allow again" (DELETE), a new timer, or the midnight after `ends`.
- No household details in committed files (`kid1`/`kid2`, `host-a`).
- Work on branch `timers`; commit per task; the user lands it.

## Review Focus

1. **A timer that ends after midnight** (started 11:50pm for 30 min): applies until the midnight after `ends` — tested in Task 1.
2. **Timer and an earlier bedtime:** the schedule's lock comes first and its warnings count to the earlier time — tested in Task 1.
3. **Games mode with no budget configured:** the Games category still gets a countdown and is used up at `ends` — tested in Task 1.
4. **Starting a timer while one has ended:** the new one replaces it, releasing the stop immediately — tested in Task 2.
5. **Old snapshots without `timer`:** still parse — tested in Task 1.

### Task 1: `Timer` and `decide_with_timer` (protocol)

**Files:** `crates/protocol/src/rules.rs`, `crates/protocol/src/lib.rs`

**Produces:**
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum TimerMode { Lock, Games }
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct Timer { pub ends: NaiveDateTime, pub mode: TimerMode }
impl Timer { pub fn stop_until(&self) -> NaiveDateTime /* midnight after ends */ }
pub enum Computer { …, TimerEnded { at: NaiveDateTime } }   // serialises as {"state":"timer_ended","at":…}
pub fn decide_with_timer(day, blackouts, used_secs, timer: Option<&Timer>, now) -> Decision;
// decide(...) = decide_with_timer(..., None, now)
AccountSnapshot.timer: Option<rules::Timer>   // #[serde(default)]
```

- [ ] Tests first in `rules.rs` (each a separate `#[test]`): lock timer before end → allowed, `next_change == ends`;
  at/after end → `TimerEnded { at: ends }`, `next_change == stop_until`; after `stop_until` → allowed; blackout wins over
  an ended timer; ended timer wins over outside schedule; schedule ending earlier → `next_change` is the stretch end;
  games timer before end with no budget → Games status `left_secs == ends - now`, not used up; with a 60-min budget and
  10 min used and the timer 20 min away → `left_secs == 1200`; after end → Games used up, computer allowed; timer
  started 23:50 for 30 min → at 00:10 next day not yet ended, at 00:20 ended, still ended at 23:59, allowed at 00:00 the
  day after. In `lib.rs`: a snapshot JSON without `timer` parses with `timer == None`.
- [ ] Implement. Commit `feat(protocol): add timers to the decision function`.

### Task 2: Server

**Files:** `crates/server/src/{db.rs,api.rs,main.rs}`

**Produces:** table `timer(user PRIMARY KEY, started INTEGER, ends TEXT, mode TEXT)`;
`Db::{start_timer(user, minutes, mode, now_local) -> Result<Timer>, cancel_timer(user) -> Result<bool>, timer(user, now_local) -> Result<Option<Timer>>}`
(`timer()` returns `None` once `now >= stop_until`); `decision()` and `snapshot()` include it; prune deletes passed timers;
`POST /api/timers/{user}` `{minutes, mode}` → 201 `{ends}`; `DELETE /api/timers/{user}` → 204/404; status users gain
`timer: {ends, mode, ended} | null`; `decision_key`/event detail handle `TimerEnded` ("timer ended").

- [ ] Tests first: db round trip, replace, cancel, expiry after `stop_until`, snapshot carries it, decision blocks after
  end; API validation (0, 241, unknown mode, unknown account), start → status shows it, cancel → gone, a new timer
  replaces an ended one; event detail "timer ended"; both routes in the login-check list.
- [ ] Implement. Commit `feat(server): start and cancel timers`.
